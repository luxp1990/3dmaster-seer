Here is a comprehensive architecture and optimization review focused heavily on stability (hang/crash prevention) and fluency (performance), as requested.

### 1. Architecture Map
The project is a Qt-based C++ dynamic library plugin (`3dmaster.dll` / `.so`) built for the Seer host application.
- **`src/plugin_entry.cpp` (Plugin Boundary):** Implements `MasterPlugin` exposing `ViewerPluginInterface`.
- **`src/master_viewer.cpp` (Presenter / Controller):** Subclasses Seer's `ViewerBase`. Orchestrates the layout (widget/sidebar) and manages the async `ModelLoaderWorker` thread lifecycle.
- **`src/master_widget.cpp` (View - 3D Renderer):** `QOpenGLWidget` subclass for rendering. Handles VBO/VAO/IBO creation, camera arcball math, and frame-by-frame rendering.
- **`src/master_sidebar.cpp` (View - UI Controls):** Sidebar containing camera presets and rendering/visibility controls.
- **`src/model_loader_worker.cpp` (Service / Data Access):** The background worker parsing files. Implements custom native parsers for STL, OBJ, PLY, 3MF and delegates CAD formats (STEP, IGES, glTF) to OCCT. Handles PRT translation via external processes.

### 2. End-to-End Data Flow & Where the Time Goes
When a user selects a file:
1. **Startup & Handoff (Minimal time):** Seer loads the DLL, constructs `MasterViewer`, and spins up `ModelLoaderWorker` on a `QThread`.
2. **Parsing & Tessellation (The Heavy Lifting):**
   - **For PRT (IPC & Parsing):** Scans the registry to find `step214ug.exe`. Launches it via `QProcess` (IPC). The time here is dominated by Siemens NX translation logic + pipeline flushing.
   - **For CAD (STEP/IGES):** Time is spent in OCCT parsing the file (IO), identifying B-Reps, and then discretizing (`BRepMesh_IncrementalMesh`). Tessellation is CPU-heavy.
   - **For Mesh (STL/OBJ/etc):** Time is dominated by CPU string parsing (`QTextStream`) for text formats and byte streaming for binary formats.
3. **GPU Upload (First Render):** The `ModelDataPtr` is passed to the main thread. `MasterWidget::buildBuffers()` iterates and allocates VBOs/VAOs in VRAM. This blocks the main UI thread momentarily.
4. **Interaction:** Render loops read directly from VRAM (`glDrawElements`). Time here goes strictly to vertex/fragment shading on the GPU.

### 3. Stability: Hang & Freeze Risks
- **External IPC Pipeline Deadlocks (Mitigated but fragile):** The `.prt` translation loops over `proc.state() != QProcess::NotRunning` with a `timeoutMs = 60000` (60s). It also attempts to read stdout/stderr. If the NX process produces *huge* amounts of output without `readAllStandardOutput()` being called frequently enough, the OS pipe buffer fills up, and the child process will hang indefinitely (deadlock). The worker handles this by actively polling and appending byte arrays in the 60s loop, preventing deadlocks.
- **Blocking CPU Work (Mitigated):** File loading is strictly offloaded to a `QThread`. The main UI (and Seer host) remains responsive.
- **Cancellation Unresponsiveness:** The `ModelLoaderWorker` makes checks against `m_cancelRequested`. However, if OCCT locks up during an expensive topological operation (`IGESControl_Reader` or `BRepMesh_IncrementalMesh`), cancellation won't process until the atomic OCCT block returns.

### 4. Stability: Crash Risks (Memory Safety & Size limits)
- **Unbounded Parsing / Memory Exhaustion (High Risk):** There are no strict file size limits (e.g., rejecting files > 500MB). A heavily subdivided STL/OBJ file will cause `QVector` expansion on the CPU to allocate hundreds of megabytes. This can trigger an Out-of-Memory (OOM) crash in the host process, taking down Seer.
- **Corrupt File Resilience (Medium Risk):** The codebase wraps OCCT calls in C++ `try { ... } catch (const Standard_Failure&)` to trap kernel aborts, but native parsers (STL/OBJ) are largely dependent on stream safety. A malformed binary STL could cause unbounded vector reserve loops.

### 5. Fluency: Memory Behavior During Interaction
- **Memory Duplication (High Impact):** When `MasterWidget::buildBuffers()` creates OpenGL buffers, it copies `ModelData::meshes` (CPU `QVector`) into VRAM. It **never clears** the CPU `QVector`. For a 50MB model, this means 50MB of CPU memory and 50MB of GPU memory are occupied simultaneously for the entire lifespan of the preview.
- **Interaction Stutter (Low Risk):** The `mouseMoveEvent` updates quaternions (`m_rotation`) and calls `update()`. No geometry is copied, no dynamic memory is allocated during rotation. The projection matrix math is minimal. Frame rates should be extremely fluent once the buffers are uploaded.

### 6. Prioritized Optimization Opportunities

| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
